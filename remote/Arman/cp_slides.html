openpilot → STÄHLE TrackDriver curvepoints

Real-time conversion of openpilot's planning / GPS trajectory into the client's curvepoint formats — for porting openpilot's driving onto the bus.

The bus is actuated by a STÄHLE TrackDriver robot that follows curvepoints (a track defined as position + heading + curvature + speed). Our job: take what openpilot plans/drives and emit it in exactly the frame and sign convention TrackDriver expects, live, from the existing reg_export telemetry stream.

Deliverables: cp_export.py (writes both formats, live & record), cp_view.py (watch while driving), plus pure-math frame.py / curvepoints.py.

3 / 8

Two coordinate frames — and why they differ

openpilot (Calibrated/Car frame — where modelV2.position lives):

  • x = Forward, y = Right, z = Down
  • heading = NED yaw (0 = North, + toward East)
  • curvature κ > 0 = turning right

STÄHLE / client (ENU, origin fixed once at mission start):

  • x = East (θ=0), y = North (θ=+π/2)
  • θ counter-clockwise positive, range ±π
  • κ = 1/R, left turn positive
  • velocity always > 0

Both a rotation (frames) and a sign flip (κ handedness) are required — the main source of bugs, so every step below is unit-tested.

4 / 8

The transforms (verified)

position :  (E,N) = WGS84_geodetic2enu(lat, lon, ref)      # ref set once, never changed
heading  :  theta = pi/2 - yaw_ned                        # North→pi/2, East→0
path pt  :  E = E0 + fx*cos(theta_veh) + fy*sin(theta_veh)   # fx=Forward, fy=Right
            N = N0 + fx*sin(theta_veh) - fy*cos(theta_veh)
curvature:  recomputed in ENU  →  left/CCW turn is naturally positive

Rather than negate openpilot's right-positive κ by hand, κ is recomputed directly on the ENU points — in an (East, North) frame the standard curvature formula makes a counter-clockwise (left) turn positive automatically, matching STÄHLE.

facing / turnexpectedtest
yaw 0 (North)θ = +π/2✔
yaw π/2 (East)θ = 0✔
left / CCW arc Rκ = +1/R, left✔
right / CW arc Rκ = −1/R, right✔
5 / 8

STÄHLE curvepoints + the distance rule

Native "10000" layout, one row per point:

Deltatime_s, velocity_kph, gear(99), index,
PositionX_East_m, PositionY_North_m, theta_rad, kappa_1pm, long_accel(=0)

Point spacing follows the PDF exactly — denser when slow, capped when fast, so the controller always has enough look-ahead:

d = v[kph]/3.6 * 0.3      clipped to  [0.6 m, 5.0 m]
   = clip(v_mps * 0.3, 0.6, 5.0)

v=1 m/s → 0.6 m (floor) · v=10 m/s → 3.0 m · v≥16.7 m/s → 5.0 m (cap). Velocity is floored above 0 so the track never stalls the vehicle.

6 / 8

Client segment format (line / arc)

{ "ref": { "latitude": .., "longitude": .. },
  "segments": [
    { "start": {"x":E,"y":N}, "end": {"x":E,"y":N},
      "velocity": <m/s>, "radius": <m, 0=straight>, "direction": "left|right" } ] }

Consecutive curvepoints are grouped by curvature into straight (|κ| small → radius 0) and arc (radius = 1/|κ|, direction from κ sign) segments. Per the PDF tip, the straight→arc threshold point keeps the straight's κ=0 to avoid interpolation overshoot.

This is a sign-correct approximation; the client's own wrapper does the authoritative segment fit. Units: segment velocity kept in m/s (matches the client example), STÄHLE curvepoints in kph — flagged in the README.

7 / 8

Watch it live — and eyeball the signs

python3 cp_view.py --ip <comma_ip> — North-up ENU map (the client frame): curvepoints laid by the distance rule, coloured left / right / straight; ego + heading arrow; the ref origin; and a top-left delay indicator. Tiles show θ, κ + direction, radius, velocity, position.

Steer left → track bends CCW, κ>0, DIR LEFT. If it ever reads inverted on the real car, the yaw / y-sign assumption is wrong and is fixed in one place (frame.py).

8 / 8

Modes, assumptions & hand-off

  • live — each modelV2 frame → the planned path ahead, transformed to ENU, written ~20 Hz to track_live.{csv,json} (with a short ego-history tail for points behind).
  • record — accumulate the driven GPS route, emit the whole route_track.{csv,json} on exit (with GPS smoothing).
  • ref origin — set once: --ref-lat/--ref-lon, or the first valid GPS fix; never changed.

Assumptions to confirm with the client: segment velocity unit (m/s vs kph); whether they prefer the STÄHLE curvepoints directly or the segment JSON through their wrapper. Both are produced, so either path works.

All conversions are covered by --test / --selftest in frame.py, curvepoints.py, cp_export.py, cp_view.py.
